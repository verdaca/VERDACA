# ANALYSIS 1 — Plan vs Reality (Technical)

## 🏗️ Winston — System Architect

Let me give you an honest architectural read, stage by stage, then name the two shifts that actually matter.

**The scoreboard — what the plan promised vs. what shipped:**

| Stage | Plan target | Delivered | Verdict |
|---|---|---|---|
| 1 Pi-Mono | Measurement foundation | 96% cov, adapter live | ON PLAN |
| 2 Compression | 65–75% token reduction | 30.34% heavy / 14.32% compound | **UNDERSHOT** |
| 3 Memory | 30–50% savings on repeats | 58.6% savings | **OVER-DELIVERED** |
| 4 Runtime | 16 agents + MCP + 20 tools | Shipped, 97% cov | ON PLAN |
| 5 MAC | +20% quality at 2.3x cost | +47% vs vanilla, +21% vs enhanced | **OVER-DELIVERED** (with A4 caveat) |
| 6 Studio | +25% vs single-agent on 10 Qs | 10/10 beat-count, +47% headline | **OVER-DELIVERED** (with A4 caveat) |
| 7 Shell | UI + Clerk + Stripe + POV harness + dashboard | UI/auth/billing/harness shipped; dashboard deferred | MOSTLY ON PLAN |

So: every technical idea in the plan has a corresponding artifact in the code. No layer was skipped. That's the good news and it matters — the 8-layer "box" is structurally intact.

**Now the two architectural truths we need to speak out loud.**

**First — the compression shortfall is real and the headline moved.** We promised 65–75% and shipped 30.34%. That's not "within tolerance," that's a different product claim. TONL delivered, but the compound stack (Forge + RTK + Caveman on top) didn't multiply the way the plan modeled. The architectural read: we over-indexed on stacking four compression techniques whose savings are *not* orthogonal — they compete for the same redundancy. Pragmatically, the right move is to retire the 65–75% claim from every external artifact and re-anchor on what we *did* beat: the +58.6% memory savings on repeats and the +47% quality headline. Those are durable. The compression headline was speculative and the measurement foundation we built in Stage 1 is exactly what caught it — which is the system working as designed. Painful, but honest.

**Second — the Praxis-to-Verdaca rename.** Shipping Verdaca-branded UI on top of 477 files in `src/praxis/` and a `pyproject.toml` that names `praxis-*` packages is *architecturally safe for now* and *a debt that compounds*. Safe, because namespace-level naming is an internal contract — customers never see `import praxis`. Compounding, because every new module, every new test, every new agent added to `src/praxis/` deepens the rename surface area. The right frame: treat the codename as a stable internal identifier (like Linux kernel module names that never match marketing), OR schedule the rename as a dedicated sprint before Stage 8 adds more surface. Don't do it piecemeal — that's how you get half-renamed codebases that confuse every new contributor for five years. My recommendation: hold the line on `praxis` internals through Stage 8, then do it atomically.

**The two latent issues that *are* architecture, not QA:**

- **A4 deferral** — our quality headline is algorithm-scored, not human-validated. Until Stage 7 closes this with ρ ≥ 0.6, every "+47%" in a customer deck is an unfinished claim. The caveat discipline in the memory ledger is correct; don't drop it.
- **C-4 Memory promotion path** — `mac.reuse_successful` has no production caller. The memory layer *works* in single-shot benchmarks, but the cross-session learning loop — which is half the Stage 3 thesis — is unwired. That's the single most important technical debt on the ledger. Fix it before scaling POVs, not after.

Net: we built what we designed. We over-delivered on the durable claims (memory, quality). We under-delivered on the speculative one (compression). And we have one architectural loop (C-4) that needs to close before we can honestly say the system learns.
